## 前提

本指南写给执行接入的 Agent。用户选择“完整接入”或“针对项目适配”，你负责调查、整理改动、实施、检查、修复与交付；不要把配置表、检查命令或逐文件操作交给用户。不依赖独立安装器，也不要求用户记住 Skill。两种方式都必须携带 [Agent 项目补充规程](../project-setup.md)，由 Agent 持续维护缺口和确认记录。

这是执行规程，不是目标项目已接入的证明。只有收到明确接入请求才修改目标项目；仅阅读、讨论本指南时不要执行接入。普通业务任务不重复接入。

### 识别输入与工作范围

- **接入方式**：沿用用户已选择的方式；没有选择时只说明两者差别并询问一次，不自行切换。
- **目标项目**：从当前工作区和用户指定路径确定；存在多个候选且无法判断时询问准确路径。不能默认把 KnowTrail 产品仓库当成目标。
- **KnowTrail 来源**：定位包含本指南、规则、脚本、模板的可读本地来源或已明确的版本。记录提交/版本；来源含未提交改动时也记录实际文件摘要，不仅记录 HEAD。
- **已有约定**：先读目标项目已有 AGENTS 和命中规则，再读来源的内核、task-start、scripts/README 及本指南。来源文件是待整合内容，不授权覆盖目标项目规则。

两种方式保留相同核心能力：判档、规则读取、构建与测试、失败修复、Wiki、沉淀和跨会话。完整接入采用标准结构；项目适配保留已有组织方式并实现等效能力。可选 version-sql 和定期复核提醒默认关闭，不为“完整”而全开。

## 步骤

### 1. 调查项目并建立基线

在目标目录检查 Git 状态、现有未提交改动和当前分支；定位 AGENTS、全部适用 MDC、Wiki、源码模块、构建/测试、迁移和 CI 入口。检查 Bash、Python、Git、ripgrep 与实际 JDK/构建工具，优先使用项目 Wrapper 或已有命令。

从构建文件、现有脚本和文档获取事实，区分已生效约定、源码观察和待确认建议。源码目录、DO/Entity 命名及局部写法不构成新增项目 MDC 或专用 glob 的授权。不扫描运行配置以收集凭据，不替用户选择 ORM、鉴权模型或数据库。

记录本次将改动文件的原始内容、来源摘要和文件归属。保持用户已有修改，不自动 stash、reset、commit 或 push。需要隔离验证时使用临时副本；不要为了制造错误改坏用户正在工作的目录。

### 2. 建立接入清单

先形成具体文件与能力映射，作为本次接入记录。保存在目标项目 `.local/knowtrail/adoption.md`；该位置已占用且不是接入记录时选择不冲突位置并在目标 AGENTS 中指明。适配模式中 workflow 路径不同则使用实际工作流目录。不要覆盖历史验收证据，重跑时追加本次结果。

| 内容 | 完整接入 | 针对项目适配 |
|---|---|---|
| 入口 | 将工作流路由合并到目标 AGENTS | 在已有总入口中整合加载与收尾逻辑，保留业务指引 |
| 规则 | 引入通用 .cursor/rules；项目自定义由补充规程处理 | 复用已生效规则，处理入口和目录冲突；不自行制定业务规范 |
| 运行文件 | workflow/task-start.md、scripts/、templates/、必要 guides/、config.json | 按实际位置映射整条读取和执行链，不只改说明 |
| Wiki | wiki/ 的模板、schema、根索引；模块内容按已确认资料整理 | 保留原资料，划定受管范围，适配格式与索引或使用独立子目录 |
| 看板 | 默认包含 workflow/dashboard/ | 同步其来源路径与场景；用户明确不采用时才省略 |
| 项目构建 | Maven/Wrapper 或配置真实自定义命令 | 接入已有构建/测试，保留工具链与模块选择 |

两种模式均交付 project-setup.md，并在 `.local/knowtrail/adoption.md` 逐项记录补充状态。不要自动把源码包树变成已确认的业务分层。

所有引用必须有落点。需要的 guides 按 AGENTS、task-start、模板和看板的引用关系取完整集合，不遗漏间接引用；接入本指南及必要后续维护说明。初始化 Wiki 使用模板，不能把产品仓库的状态记录当成业务知识。

不覆盖目标项目 README、LICENSE、CI 或 gitignore。KnowTrail 的回归测试和仅用于维护来源仓库的说明不是默认运行载荷，不照搬。必要的忽略规则按条目合并，所引入文件需要的授权声明在不冲突位置保留，并记录来源。

### 3. 处理冲突，再实施

整理并简要展示新增、合并和适配的范围。已获授权且可逆的常规改动继续执行，不逐文件索要确认。以下情况只询问无法取证的关键事实，并继续不依赖答案的工作：

- 两条业务规则实质矛盾，无法确定正确业务口径。
- 标准路径已有不相容内容，完整接入无法保留；说明具体冲突，由用户决定是否改用项目适配，不能悄悄切换。
- 缺少目标路径、必需来源，或必须进行接入范围之外的破坏性动作。

不要通过覆盖原文件、删除业务硬门禁、重复 alwaysApply、关闭必需检查或额外层层转发来掩盖冲突。接入不包含数据库写入、生产测试、发布和远端权限变更。

### 4A. 执行完整接入

1. 使用标准路径：AGENTS.md、.cursor/rules/、workflow/、wiki/；保留业务源码与构建文件原布局。
2. 合并目标 AGENTS 的分层、规则加载与收尾入口，保留原有业务约束。移除仅适用于 KnowTrail 产品仓库的“无业务 POM”等来源仓库说明，不让其进入业务项目入口。
3. 引入完整通用规则与脚本，接通工作流自身引用。不根据源码命名匹配或新增 DO、Mapper、Job 等项目专用 glob；项目规则的补充遵循 project-setup.md。
4. 由 Agent 建立项目补充记录，引用已有生效约定；将源码观察和建议列为候选，不直接转为规范。只询问无法自行取证且影响当前任务的内容。
5. 初始化标准 Wiki 模板与索引。已有同名资料先合并；业务模块依据已确认资料整理，未知时保留待补项，不批量生成目录说明冒充知识。
6. 保留构建/测试入口，依据已生效约定配置，不自动安装或切换 JDK。用户排除编译时只验证本次适用范围，明确未验证项；生成看板并进入分层验收。

### 4B. 执行针对项目适配

1. 为每项能力标记“复用、配置、适配实现或待补”，列出真实规则、触发条件、执行入口和验收用例。
2. 以现有 AGENTS 为总入口，合并流程语义；保留业务规则并消除重复内核，不能保留两套互相矛盾的判档和收尾。
3. 串联修正路径：规则文本/glob → 配置 → 脚本 ROOT/调用/import → Wiki/schema/字典/handoff → 文档链接 → 看板。检查生成器和校验器的固定路径，不能用一个配置值替代整条适配。
4. 将构建、测试和迁移检查接到项目已有命令；命令返回失败必须传播。已有等效检查可复用，但记录其覆盖能力与测试证据，不能因“项目已有脚本”而跳过验证。
5. 已有 Wiki 不一致时，优先在其内部划出使用标准模板的受管子目录，历史资料作为来源；如确需等效格式适配，保留元数据、来源、索引及症状要求，不加无限豁免。
6. 为每个适配点增加正反验证，在受管范围内执行共同验收。没有接通的必需能力记为待补或失败，不标为不适用。

当前代码仍有固定的 workflow/config.json、ROOT、MDC 和文档路径假设。不得将文件整体搬入新目录后宣称可用；如果适配涉及运行实现，先阅读、修改并验证相关代码，无法完成则记录准确缺口。

### 5. 验收、修复与试运行

先区分基础接入、项目补充与业务验证。以下完整收尾与业务试运行仅在本次范围允许且前提具备时执行；否则逐项运行适用的非构建检查，不能用 SKIP_COMPILE 假装完整收尾通过。默认范围扫描包含用户既有未提交变更，先核对归属，避免接入检查意外触发编译。

由 Agent 运行下节验收。先确认实际入口，再执行命令；标准结构可使用下面的入口，适配后使用映射中的真实路径，禁止在来源仓库跑过就当目标项目通过。

```bash
# 工作目录必须是目标项目；仅在对应标准路径确实存在时使用。
python3 workflow/scripts/wiki/wiki_metadata.py --write
bash workflow/scripts/finish-audit.sh
python3 workflow/dashboard/build-workflow-page.py
python3 workflow/dashboard/build-workflow-page.py --check
```

元数据同步只针对已确定采用本模板的 Wiki 受管范围，不能拿它批量修改未经接管的旧文档。构建与测试按已查明的项目命令执行；完整收尾本身不保证自动运行全部测试。

在隔离副本中验证失败注入和修复，随后验证目标实际状态。失败先修复再重跑受影响检查；不得只修改输出、关闭检查或删除失败用例。共享构建产物的命令串行执行。

试运行优先使用已有、已授权的低风险任务；没有业务任务时，在目标项目隔离副本中选真实模块做可撤销的验证改动，不擅自新增业务功能。使用新会话验证 handoff；当前工具无法创建或使用独立会话时如实记为待验证，不让用户记一串验证命令，也不伪造会话证据。

### 6. 交付与后续维护

给用户简明结论：所选方式、改动范围、已接通能力、实际验证结果、未完成事项及接入记录位置。不要只说“文件已复制”。本次接入完成后，正常需求按工作流推进，不重复跑初始化。

接入记录至少包含：来源版本与实际摘要、目标分支/基线、文件归属与修改清单、能力映射、命令/操作与退出结果、Agent 读取与跨会话证据、状态、恢复办法。升级对比旧来源、本地内容与新来源；仅更新无冲突上游文件，项目规范与 Wiki 不覆盖。回退只恢复本次引入的内容，不用整仓重置；入口或根路径变化后重跑完整验收。

## 示例

### 用户只选择方式

用户：“按完整接入方式，将 KnowTrail 接入当前 Java 项目。”

你应定位目标和来源，保留基线，接通标准工作流，维护项目补充记录并验收。不要按 DO 等源码命名自动制定规范；不要要求用户复制文件、执行检查或填写整张技术表格。

用户：“按针对项目适配方式接入，保留现有规范和知识库。”

你应调查现状、建立能力映射并处理实际冲突。比如 Wiki 在 docs/knowledge/，同步修改入口、MDC、配置、schema、字典、handoff、链接及看板，分别验证。不能只改 wiki_root 就报告完成。

### 接入记录格式

| 能力 | 目标实现/触发 | 验证操作 | 实际结果与证据 | 状态/下一步 |
|---|---|---|---|---|
| 按目标项目逐项填写 | 实际文件或命令 | 正向、反向及修复复验 | 日志位置、退出码或读取记录 | 通过/失败/待验证/不适用及理由 |

表格是记录格式，不是已通过的样例；尚未执行的项目不能预填成功。

## 验证

### 两种方案共用的验收集

| 能力 | 正向场景 | 反向或边界场景 | 通过证据 |
|---|---|---|---|
| 入口与规则加载 | 从全新会话发起单点任务，找到项目规范与适用 pack | 不直接打开 SQL/Wiki 文件，仅以结构变更语义触发；中途扩大范围补读 | 实际读取动作/文件记录及规则依据，不能只凭 Agent 声称已读 |
| 判档 | 配置数据、已有方法修改、新接口/结构变化分别走相应档位 | 单点不强行完整化；轻量仍执行命中的规则 | 任务输入、判档依据、执行步骤相符 |
| 改动范围 | 暂存、工作区、未跟踪文件和显式分支基线都能识别 | 暂存错误不能被未暂存的修正隐藏；未知基线明确失败 | 文件范围与 Git 实际差异一致 |
| 构建与测试 | 用项目真实命令验证受影响范围 | JDK 不匹配、构建失败、测试失败均不能报告成功；共享产物串行构建 | 命令、环境、退出码；测试不能用 compile 结果代替 |
| HTTP 提示 | 常见 Mapping 差异被报告，包括非 Controller 命名路径 | 普通路径变化不自动强制鉴权规则或文档平台 | 差异输出与实际变化一致；非 Spring 项目记录对应适配验证 |
| JOIN 与索引 | 关联基数、ON/WHERE、访问路径、批量上界有证据 | 关联未知、连接放大或缺少计划时不伪称已核验；不执行数据库写操作 | 查询到索引的核查记录、结论与证据缺口 |
| 结构交付 | 按目标项目迁移方式交付并同步字典/关联说明 | 可选格式未启用不误拦截；启用后缺回滚段或改冻结记录会失败 | 项目原检查或选定检查器的正反结果 |
| Wiki | 新专题、模块 README、总索引、来源及可见标题同步 | 在副本中引入坏链接、缺章节、漏症状索引，确认失败；修复后通过 | 文档与检查输出；长期未更新不阻断 |
| 失败修复闭环 | 失败 → 返回修改 → 再检查 → 交付 | 必需脚本异常不能当通过；可选复核提醒异常只报告未完成 | 失败与修复后两次独立结果，交付对应修复后的文件 |
| 沉淀与跨会话 | 有新经验才记录，另一新会话能找到 handoff 继续 | 无信号不造文档；用户私有记录不进入公开看板 | 新会话实际恢复上下文、任务结束时状态更新 |
| 看板 | 更新后规则、路径、脚本链与目标项目一致 | 生成失败保留旧页；不嵌入 local 私有规则 | 页面交互与文件快照核对；不能把看板当运行报告 |
| 接入可恢复 | 在隔离副本重复应用接入步骤，不重复追加入口 | 存在用户改动的文件不能覆盖；恢复只影响本次改动 | 应用前后及恢复后的 diff；知识内容保留 |

脚本能力与 Agent 核查分开验收。脚本无法证明 JOIN 语义、规则确实被读取或 handoff 真正恢复，不能拿脚本全绿替代这些场景。

本体的回归测试只证明包自身行为，不能代替上述目标项目验收。只使用一种 IDE 的项目验收该 IDE；声称支持 Cursor 和 Codex 时两边分别验证。涉及 shell/路径的平台也按实际目标平台测试，不把 macOS 结果外推到 Windows。

### 验收状态与退出条件

三个维度分别记录，不能压成一个“全部通过”：

- **基础接入**：本次通用文件链、入口引用、配置读取、门禁正反与修复、Wiki 格式及看板验收通过，才可报告基础接入完成。已发现基础故障必须修复；缺少证据记待验证。
- **项目补充**：按 project-setup.md 记录待取证、待确认、已落实或不适用。未补齐不自动否定基础接入，但相关业务能力不能宣称已就绪。
- **业务验证**：编译、测试、运行、JOIN/索引语义和新会话实际执行分别提供证据；用户排除或本轮未做时如实列出，不冒充通过，也不变成永久豁免。

不适用只用于明确可选或项目不存在的能力，并记录理由。目录/规则适配需要验证实际调用链，不能用关闭门禁换取通过。一次真实项目验证只覆盖当次模式、环境和测试场景，不能外推所有项目都可无差异接入。

## 常见问题

### 用户是否还要运行命令或填写规范？

用户无需执行命令或填写空表。Agent 按项目补充规程查找资料、维护记录、落实已生效约定，只就缺少的业务事实或必要选择发出具体问题；使用者决定项目约定，Agent 不用源码观察代替这一决定。

### 两种方式是否功能不同？

核心能力相同，目录与实现方式不同。完整接入也保留项目事实和可选检查的默认关闭状态；项目适配必须证明等效能力，不靠关闭门禁过关。

### 没有测试、构建工具或新会话能力怎么办？

继续完成不受影响的部分，分别报告基础接入和业务验证状态。缺构建环境不应被写成构建通过；基础文件和门禁可独立验收。不能默认安装工具或更换 JDK。

### 这是已经验证适用于所有项目的一键方案吗？

不是。这是 Agent 执行入口与验收规程；每个目标项目都要实际验证。当前不提供安装器，不把本体回归通过、格式检查通过或源码静态阅读当成真实接入成功。
